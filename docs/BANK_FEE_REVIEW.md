# 覆核手續費一致性

人事明細與發票分組明細共同顯示「手續費負擔」及「公司手續費」，包含 0 元。負擔選項沿用「己方支出／對方支出」。摘要是檢視資訊，不提供不能保存的編輯控制項；金額與科目的既有覆核權限不變。

## 資料來源

- `bank_fee_amount` 是已保存單據及正式入帳的費用來源，讀取、保存及覆核不能依目前費率重新計價，也不能因「非兆豐銀行」含有「兆豐」而歸零。
- 新申請及總務明確重新填寫付款資料時，才依當次銀行、負擔方及法人費率計算。總務更新使用新付款資料，避免沿用舊的 0 元或 15 元。
- 人事匯款按正數金額的每列銀行判斷；中文與既有英文銀行欄位、017 分行代碼、空白列的整批選項，與補件後端一致。銀行帳號不能充當銀行代號。
- 人事非兆豐匯款筆數與負擔方、費率分開計算；對方支出或費率為 0 時仍保留正確筆數，讓重新送件通過相同後端檢核，公司手續費維持 0。
- 一般補件不傳送空的電子勞報保留欄位；只有電子勞報表單才傳送其專用資料，避免被後端欄位白名單拒絕。
- 未取得已存費用時顯示「尚未確認」。原人事試算與已存費用不一致時提示會計核對，不自動回填歷史單據、付款或傳票。
- 電子勞報由其付款流程確認；預支首次撥款後的最後核銷不重複加計。

後端 migration `20261016043221_finance_bank_fee_classification_v1.sql` 只更正申請人補件函式的兩處銀行判斷；授權、步驟、版本檢查、冪等鍵及稽核保留。來源雜湊或權限不符即停止，正式資料不回填。

## 驗收

- `pnpm test:bank-fee-review`：實際前端函式、API 映射與序列化，涵蓋已存 0 元、多筆費用、費率變更、缺值、矛盾資料與字串跳脫。
- `pnpm test:bank-fee-review-browser`：Chromium／WebKit、1440／390 寬度、兩種明細版型與兩個詳情入口，以及會計、執行長及一般員工。使用虛構資料，不連接正式資料庫。
- `pnpm test:procurement-closeout`：實際總務 handler 與隔離 PostgreSQL 防護，驗證 0→15、15→0 的負擔／銀行更新、原子保存、本金及付款狀態。
- `pnpm test:bank-fee-classification`：舊後端重現、新版實際補件函式、重送與拒絕案例，以及封存發布、交易回滾、權限與版次驗證。
- 完整 `release:preflight`、CI 與受保護發布流程仍為必要條件。正式發布須核對同一候選 manifest 與資料庫 postflight；本機驗收不代表已上線。
