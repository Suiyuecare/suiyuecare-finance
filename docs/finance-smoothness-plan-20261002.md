# 財務系統順暢度改善與驗收（2026-10-02）

本計畫把「操作像熟悉的手機 App 一樣順」定義為：輸入不被背景作業卡住、畫面先顯示已確認且可用的內容、長工作有真實進度、失敗可以安全接續。財務數字、權限、簽核及送單結果仍以正式資料庫的權威讀回為準；逾時不可顯示成 0 筆、成功或失敗。

## 量測基線與邊界

- 目前正式版來源為 `29efb7e31fef2f1ef7eaa289098ca7bf6daffee5`。匿名冷快取、390px、150 ms RTT、4 Mbps、4 倍 CPU 降速下，登入畫面可操作 5 次為 2.585–2.964 秒；這不代表員工 Google 登入後的工作頁面均在 3 秒內。
- 首頁 HTML 解壓約 2.91 MB、傳輸約 742 KB。首屏已接近 3 秒，後續需檢討按頁載入與初始解析量。
- 本批草稿直傳與同檔重存會減少暫存時的轉碼和重傳；暫存後正式送單仍須依原流程合併憑據與歸檔，尚未證實提速。不能把此批說成所有附件上傳皆已加速。
- 正式帳務資料不得為了速度而改成推估值、部分分類帳、錯誤的 0 筆，或略過後端授權與入帳檢查。無登入憑證時只能以虛構角色、正式站匿名畫面及正式資料唯讀統計驗收；不能宣稱每位員工本人都已操作。

## 發布門檻

1. 所有本批新增與既有關聯測試通過；失敗、逾時、切換帳號與重複動作皆有可恢復狀態。
2. 1440px 與 375／390px 實際瀏覽器檢查搜尋、草稿、附件和簽核畫面，保留可操作的鍵盤與觸控路徑。
3. `pnpm release:preflight`、受保護的 GitHub release gate 與固定候選發布均通過；正式站 `release-manifest.json` 必須是相同 commit。
4. 正式站只讀確認主要路由與資源可載入，且無新的登入、附件或送單錯誤。真實員工帳號體驗的 p95 要以匿名化、分角色的後續量測核對，不以本機 fixture 取代。

## 後續批次

分類帳／簽核摘要後端快照、50 MB 附件的可續傳上傳、工作清單的任務式手機卡片，均需另保留資料完整性與現有權限的完整回歸。每項應單獨量測前後與發布，避免把大規模改版和送單核心交易綁成一次高風險發布。

## 第二輪實測與改善順序（2026-10-02）

第一輪正式版 `fa6bd2b02b93894fefa935841f88026c8ee2b4e8` 的匿名 390px 冷啟動，在 150 ms RTT、4 Mbps、4 倍 CPU 降速下，五次登入按鈕與處理函式可用時間為 2.591–2.937 秒；同一瀏覽器的五次暖重載為 1.614–1.653 秒。每次載入仍須傳送 746,229 bytes 的首頁 HTML、解碼後 2,929,599 bytes。這是匿名入口的量測，不能推論登入後儀表板、草稿或簽核也在 3 秒內。

本輪依使用者能否立即開始工作排序：

1. 將龐大的內嵌主程式做成有雜湊檔名的同網域靜態資源，讓短 HTML 先完成、重訪能重用程式快取。冷、暖都須重新量測；冷啟動若因多一次請求變慢，須如實記錄。
2. 本人草稿先顯示已取得且有權限的第一頁，後續頁繼續載入；總數、分頁及讀取失敗不得冒充完整結果，切換帳號不得留下前一人的資料。
3. 線上儀表板的應收未收只採用完整授權的後端結果，等待期間不反覆計算不會顯示的瀏覽器暫編應收。正式分類帳與公司報表設定仍要完整核對，不以局部金額代替。
4. 私有附件預覽要在簽章或媒體讀取失敗時明確停下並提供重試／下載；切換帳號或關閉視窗須清除舊媒體。
5. 帳號切換時立即退役舊帳號的整批讀取與重新整理等待，舊結果不得清除新帳號的讀取狀態。共用寬讀佇列中已執行的請求仍可能短暫佔位，留待獨立的取消與併發驗收。
6. 發票與繳費單送件跨分頁關閉時，只保留目前登入者範圍內的原交易識別碼，重開後先查正式資料；未知結果維持防重鎖，不把查不到誤判為可以重送。修補前已關閉的分頁無法追溯原識別碼，需人工核對既有正式紀錄。

同一組匿名本機 390px、150 ms RTT、4 Mbps、4 倍 CPU 限速比較顯示，程式拆分前後冷載入為 2.531 與 2.587 秒；暖重載由 1.642／1.639 秒降至 0.270／0.259 秒。這只證實入口靜態資源的快取效果，尚不代表員工登入後的財務資料或大檔上傳速度。

尚待後續獨立驗收：登入後依角色的實際 p50／p95、完整分類帳的優先讀取與舊身分傳輸取消、簽核大量歷史的資料庫查詢成本，以及正式送單 50 MB 附件的免重傳／可續傳。這些項目尚未因本輪前端驗收而視為完成。
