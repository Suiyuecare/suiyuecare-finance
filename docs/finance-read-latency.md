# 讀取效能改善與驗收（2026-09-13）

本次針對登入、儀表板、財務報表、組織診斷、簽核清單與傳票，改善使用者等待主要內容的時間。沒有把逾時縮成 3 秒、把未完成讀取當成零筆，或使用不完整分錄計算正式金額。

## 已重現與改善

| 路徑 | 改善前 | 改善後 | 量測條件與改法 |
| --- | ---: | ---: | --- |
| 初始畫面完成啟動 | 3.75 秒 | 2.72 秒 | 同一 gzip 伺服器、手機 390px、150ms RTT、4Mbps、4 倍 CPU 降速；PDF/Excel 改在操作時載入，少下載約 571KB。離線測試版本不提供 Google OAuth，此數字不是員工登入耗時。 |
| 儀表板完整財務指標 | 3.71 秒 | 1.84 秒 | 4,034 筆匿名分錄、11 家虛構公司、相同延遲 fixture；公司設定有限並行、僅必要資料阻擋指標。 |
| 財務報表主要內容 | 3.60 秒 | 1.78 秒 | 同上；隱藏的舊版分析改為展開時才計算，減少重複建模。 |
| 組織權限診斷 | 3.31 秒 | 1.10 秒 | 每組 API 固定 1,100ms；六個相互獨立的讀取同時啟動，仍核對同一身分與讀取版本。 |

以上是可重現的受控前後比較，不能當成正式環境每位員工的 SLA。正式站冷啟動另以未登入瀏覽器驗證；沒有使用真正員工的 OAuth session 或冒用其 JWT。

## 資料庫查詢

正式 `pg_stat_statements` 曾記錄申請單來源分頁平均約 7.50 秒、發票廣讀約 4.09 秒、繳費單廣讀約 3.04 秒。這些是統計窗口內的歷史聚合，包含舊版本，不是新版本的即時 P95。調查當時沒有阻塞鎖等待證據。

目前 exact-count 查詢需要對「本頁資料」及「總筆數」重複套用可見權限。新增 `finance_statement_source_page_v1` 使用同一個 MATERIALIZED 可見集合提供分頁與精確筆數；三種固定來源為申請單、繳費單、發票。

- `SECURITY INVOKER`；原本的 RLS、Google 驗證及資料寫入規則保留。
- 租戶由後端目前身分取得；前端不能傳入另一租戶。
- 每頁最多 1,000 筆，固定 ID 排序；每頁核對筆數、身分、環境與完整性。
- 合成資料的同等 RLS 工作量由 2,006 次降為 1,006 次，結果、附件欄位及精確總筆數相同。
- 只有 RPC 尚未部署的相容情況才使用既有 scoped exact-count 查詢。拒絕權限、逾時或格式錯誤都不會改用較寬的查詢。
- 繳費單也完整分頁讀取，不以原本 2,500 筆上限冒充完整集合。

資料量、網路或後端負載仍可能造成超過 3 秒。此次以消除重複權限判斷和等待依賴降低耗時；不宣稱已測得每位員工所有 API 都低於 3 秒。

全量系統健檢中的簽核快照健康檢查，也有歷史平均約 5.85 秒的紀錄。健檢改為有界並行、逐項呈現已完成結果，全部完成前維持「檢查中」，不將單一慢 RPC 偽裝成成功。送單既有的背景維運檢查與正式寫入守衛保持原規則。

## 畫面與一致性

目前頁面的來源先排入廣讀佇列，單一來源讀完即顯示。其他來源繼續更新，簽核與入帳仍要求既有正式驗證。背景完成不再重播舊傳票或覆蓋已經呈現後的新修改；切換身分、租戶、環境、權限或工作區鎖定時丟棄晚到結果。

全域更新只重畫目前頁面及導覽數量，不重畫隱藏的儀表板、所有簽核分頁與人員清單。傳票一次顯示 50 筆，搜尋與統計仍針對完整已載入集合；清楚標示已載入範圍。簽核紀錄直接呈現後端已驗證的分頁，不先計算其他分頁。

財報的來源公司設定必須成功取得才顯示正式金額；公司／部門管理分析與完整匯出仍核對全部所選公司的設定，包含沒有分錄但有預算的公司。舊分析收合時不計算、展開時重新核對。

草稿沿用獨立本人讀取與先前的完整性修正；本次納入回歸。Excel、PDF 首次操作共用一個載入請求，載入失敗保留原檔、允許重試，二進位 Excel 不會被誤當文字解析。
