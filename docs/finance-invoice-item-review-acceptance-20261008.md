# 發票與入帳明細合併驗收目標

本次範圍是費用申請的逐品項明細、員工備註，以及簽核詳情中的發票與會計科目核對。既有金額、稅額、簽核與正式入帳規則不因畫面合併而變更。

| 驗收面向 | 通過標準 |
| --- | --- |
| 一個檢核區塊 | 詳情與簽核彈窗各只有一個「發票與入帳明細」區塊；來源品項各顯示一列，不再另列一張重複的發票核對表。 |
| 發票分組 | 同張發票的品項連續放在同一有底色及左邊框的區塊；區塊標頭顯示發票號碼、日期、品項數及含稅小計。不同日期、賣方或來源檔案的同號憑據不混組。缺資料明示「未填」，不虛構發票資訊。 |
| 逐項核對 | 每列可看完整品名、數量／單價、員工備註、未稅、稅額、含稅及依原權限顯示的借貸科目；原有來源檔案及買賣方統編可展開查看。同號同日但來源不同時，標頭直接顯示差異。人工修改的金額與科目可保存，已入帳資料唯讀並以正式傳票核對。 |
| 員工備註 | 員工可在草稿及退回編輯的各品項填備註；草稿重開、送件、補件、檢核畫面及 CSV／Excel 匯出保留同一內容。補件重新送出時追加含最新備註、明確標示版次的經費明細附件，原附件保留。備註只作顯示與稽核，不改變科目、稅額或金額判斷。 |
| 關聯安全 | 新品項有固定識別碼；會計列以來源識別碼關聯。舊單僅在品名與金額組合唯一且完全相符時配對；無法確定時明示待核對，不按畫面列號猜測。採購彙總及手續費另列。 |
| 重新辨識 | OCR 重新執行時，可唯一確認的原品項保留識別碼與備註；無法確認的已填備註，在覆蓋前明確要求確認，不會靜默遺失或配給另一品項。 |
| 桌面與手機版面 | 在 1440、1024、390、320 px 實際瀏覽器下，整頁無橫向溢出；長品名、長備註、長發票號碼及大金額可換行或完整讀取，品項、金額和科目控制項不重疊、不被裁切。手機每品項為清楚可讀的卡列。 |
| 操作與權限 | 可操作輸入與選單至少 44 px 高；鍵盤焦點可辨識。申請人及一般主管不取得科目編輯權；原有會計／主管授權、簽核及正式傳票流程維持。 |
| 防重與資料一致 | 分組小計由來源品項求和，總計不重複計算；重新排版或切換尺寸不觸發寫入。兩張同號不同憑據、重複品名金額、無發票號碼及正式入帳舊單都須測試。 |
| 正式傳票差異 | 已入帳單若逐項會計明細無法與正式傳票核對，顯示明確警示、直接展開正式傳票分錄；不得把舊科目標成「已核對」，也不得讓申請人編輯已入帳資料。 |
| 發票號碼辨識 | 每張發票的標頭以「發票號碼」明示並放大號碼；可一鍵複製且以可讀狀態回報成功或失敗。未填號碼時顯示「未填」，不提供空值複製。日期與含稅小計留在同一標頭。 |
| 檢核密度 | 1440 px 檢核列的含稅、未稅、稅額橫向並列，借方／貸方科目各有明確欄名；每個品項與備註保持同列可讀。窄螢幕改為分層排版，不以縮小觸控目標換取密度。 |
| 舊單提醒 | 可唯一暫配的歷史品項在發票區塊顯示一次提醒與總數，逐品項仍保留「暫配・待核對」標示；不能可靠對應的品項仍直接標示待核對，不把暫配當成正式核定。 |

自動驗收入口：`pnpm test:invoice-item-review` 與 `node scripts/check_invoice_table_layout_browser.cjs --review-only`；後者也列入穩定性及正式發布的瀏覽器檢核。完整跨表單回歸可執行同一腳本且不帶 `--review-only`。財務人工覆核與正式傳票另由現有回歸測試驗收。圖片證據包含桌面、平板寬度與 390／320 px 手機。
