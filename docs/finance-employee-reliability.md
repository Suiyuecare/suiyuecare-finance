# 員工送件、簽核與入帳可靠性修繕

本次處理員工使用體驗檢查 E01–E10，以及送件、補件和最後會計入帳的故障恢復。正式交易結果以資料庫回應或符合原交易識別的權威讀回為準。等待逾時代表結果未確認；不代表失敗、成功或可以建立另一張單。

## 員工使用方式

- 新增申請：手機依區段填寫，下一步保留已填資料。送出前會一次列出需補充的欄位，點選提示可回到該欄位。
- 附件：選取時檢查大小；完整檔名與大小可見。可預覽支援的圖片，PDF 提供另開原檔／下載。選錯檔案可移除後重選。
- 零用金：切換申請模式會保留共同欄位、收款資訊與附件；各模式的費用列保持各自內容。
- 我的申請：每張卡片顯示目前狀態、關卡、待處理人及下一個動作。「待處理」的人不會冒充已簽核的人。
- 通知：讀取失敗會顯示失敗和重試入口；有先前成功資料時顯示最後成功時間。只有成功查到空集合才顯示零筆。
- 登入到期：重新驗證失敗或逾時仍有重試按鈕。工作區身分不一致時，保留鎖定與背景操作隔離。
- 組織資訊：清楚區分工作聯絡信箱和登入信箱；一般人員不會把登入帳號誤認為聯絡資料。
- 收款疑義：已有付款紀錄的原申請人可從詳情按「尚未收到／金額有疑義」。出納或會計在「簽核管理 → 收款疑義」查核回覆，最後由原申請人確認已解決。這個獨立流程不會重複付款、不會代替員工確認收款，也不會改動原傳票。

## 交易恢復原則

1. 正式送件保存原請求和交易識別，以同一筆請求讀回或重試，避免重複建單。
2. 補件與最後會計操作保留原版本、原動作、原明細和交易識別；不確定結果時先確認原結果。
3. 資料庫已確認交易完成後，通知或畫面讀取失敗不能把已完成入帳顯示成入帳失敗。
4. 權限、有效任職、帳號、公司、資料環境及關帳期間仍由伺服器檢查；不透過放寬權限或偽造簽核排除錯誤。
5. 登入身分或資料環境改變時，晚到的回應不得合併進另一位員工的工作區。
6. 收款疑義回報使用原 UUID 重試；版本已更新時要求重新讀取，避免覆蓋另一位承辦人的回覆。完整事件紀錄與業務交易分開保存。

## 驗證邊界

本機測試採用虛構人員、申請和附件，瀏覽器測試阻擋外部連線；SQL 測試執行實際候選函式與相關既有權限／入帳函式。這些結果不是全體員工以本人 Google 帳號登入的證明，也不代表人工查核、付款、結案或歷史會計資料已被代為完成。

發布使用既有受保護流程：精確 migration 順序、交易內 postflight、回滾演練、canary、版本與靜態資產驗證。正式環境另讀回 migration 和部署版本。網路、登入服務或資料缺漏仍可能造成操作失敗；系統必須能保留資料、區分真實結果並提供安全恢復方式。
